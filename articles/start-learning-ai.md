Our advice for starting to learn AI as a beginner is simple: use AI tools for real tasks, then build one small thing with them as soon as you can. Reading and courses help. In our view, they stick better when you have a deadline and someone looking at your work. This roadmap has four stages, and each one ends with a build small enough to finish and show.

### Why build early instead of finishing a course first?

Courses give you vocabulary. Building gives you judgment. When you try to make something work, you find out which ideas matter now and which can wait.

A hackathon or a build day can add two things that self-study often lacks:

- A deadline. A fixed end time pushes you to pick a small scope and finish it.
- Feedback. Other people see your work and react to it.

You do not need to feel ready. Read each event's description to see who it is aimed at and what it expects, and pick one that fits where you are.

### Stage 1: How do I get comfortable using AI tools?

Start as a user, not a builder. Use a chat assistant for real tasks in your own work or study: summarizing a document, drafting an email, explaining code, planning a trip. Notice where it helps and where it gets things wrong.

While you do this, learn a few core ideas in plain terms:

- Model: the trained system that produces answers.
- Prompt: the instructions and context you give it.
- Context: the information the model can see when it answers.
- Hallucination: a confident answer that is not true.

Stage 1 build: a prompt pack. Write a small set of tested prompts that solve one recurring problem for a specific group. For example, you might write prompts that help students revise for exams. Document what each prompt does, show example outputs and note where it fails. If you want to enter it in an event, read the event's rules first to see what kinds of entries it accepts.

### Stage 2: How do I make AI do something useful on its own?

Next, connect a model to a simple workflow. You can do this with a no-code automation tool or a few lines of code that call a hosted model API. The goal is a tool that takes an input, does one job and returns a result without you typing into a chat window.

Learn these ideas along the way:

- How a request goes out and a response comes back.
- How to keep API keys and other secrets out of public code.
- How to give the model a clear role, a clear output format and a few examples.

Stage 2 build: a one-job assistant. For example, a tool that turns meeting notes into action items, or one that sorts customer messages by topic. Keep the interface plain. A working form is worth more than an unfinished polished app.

### Stage 3: How do I build a real AI app?

Now add the parts that make an app feel useful: your own data, a simple interface and some way to check quality. Three patterns are worth learning at this stage:

- Retrieval: letting the model look things up in your documents before it answers.
- Tool use: letting the model call a function, such as a search or a calculator.
- Evaluation: a short list of test inputs you run every time you change something.

You may want to use an AI coding assistant here. That can save time, but read the code it writes and make sure you can explain it. Be ready to answer the question "how does this work?" in plain words.

Stage 3 build: a small app that answers questions about one set of documents, such as a club handbook or a product manual. Show where each answer came from.

### Stage 4: How do I build with agents and teams?

An agent is a system where a model plans steps and calls tools to reach a goal. Agents are easy to overbuild. A good rule of thumb is to start with one agent, two or three tools and a clear point where it stops.

This is also a good stage to work in a team. For example, a team of three might split the work this way: one person on the model and backend, one on the interface, one on the pitch and user research. Learning to split work and merge it under time pressure is a skill in itself.

Stage 4 build: an agent that completes one multi-step task, such as researching a topic and drafting a short brief with sources. Record a short demo video in case a live demo fails.

### What should every stage build include?

Use this checklist before you show or submit anything:

- One sentence that says who it is for and what problem it solves.
- A working demo, even if it covers only the main path.
- A short README: what it does, how to run it, what is not done yet.
- A note on limits: where the AI can be wrong and how you handle it.
- A short demo video or walkthrough.

Keep every finished build somewhere you can point to, such as a code host like GitHub. In our view, four small finished builds tell people more about you than one large unfinished one.
